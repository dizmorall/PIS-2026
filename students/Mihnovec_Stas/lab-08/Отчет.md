## 2. Разделение на Bounded Contexts
Монолит был разделен на 3 независимых микросервиса:
1. **Complaint Service** — отвечает за первичный прием жалоб и анализ ИИ.
2. **Moderation Service** — отвечает за работу живых людей (оценки, комментарии модераторов, репутация).
3. **Notification Service** — отвечает за рассылку Email-уведомлений пользователям и авторам фейковых новостей.

Каждый сервис имеет свою базу данных и разворачивается в отдельном Docker-контейнере.

---

## 3. API Gateway
Настроен **Nginx** в качестве API Gateway (`api-gateway/nginx.conf`).
Он выполняет обратное проксирование (Reverse Proxy) и маршрутизацию:
- Запросы по пути `/api/complaints/` направляются в `complaint-service`.
- Запросы по пути `/api/moderation/` направляются в `moderation-service`.
Это позволяет фронтенду взаимодействовать с системой как с единым целым через порт 80, не зная внутренней топологии микросервисов.

---

## 4. Асинхронная коммуникация (Event Bus)
В качестве брокера сообщений используется **RabbitMQ** (Exchange type: `fanout`).
Реализован паттерн Publisher/Subscriber:
- Когда `Complaint Service` сохраняет новую жалобу, он публикует событие `ComplaintCreated`.
- `Notification Service` подписывается на эту очередь и, получив событие, асинхронно отправляет письмо модераторам.
Это избавляет `Complaint Service` от необходимости ждать завершения отправки email (снижает Latency).

---

## 5. Отказоустойчивость (Circuit Breaker)
Реализован паттерн **Circuit Breaker** (Предохранитель) для защиты внешних синхронных вызовов (например, к стороннему API для AI-проверки текста).
Если внешний сервис падает (3 ошибки подряд), предохранитель переходит в состояние `OPEN`. Последующие запросы не ждут таймаута, а мгновенно отклоняются (`Fast Fail`), сохраняя ресурсы микросервиса. Через минуту (`HALF_OPEN`) система делает тестовый запрос и при успехе восстанавливает цепь.

✍️ Переход к микросервисной архитектуре позволил физически изолировать Bounded Contexts друг от друга.
